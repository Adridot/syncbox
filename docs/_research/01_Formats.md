## Formats d'échange Rekordbox et alternative à l'écriture directe du master.db

### Constat (faits sourcés)

**Le format XML (rekordbox.xml / collection.xml)**
- Le XML reste le canal d'échange officiel documenté par Pioneer/AlphaTheta : on importe des playlists depuis un fichier XML dans le volet **[Bridge] / "Imported Library"** via *Preferences → Bridge*. Spec PDF officielle liée depuis la page développeur · https://rekordbox.com/en/support/developer/ et https://cdn.rekordbox.com/files/20200410160904/xml_format_list.pdf (version du format = **1.0.0**, PDF daté 2020-04-10).
- Contenu du XML d'après la spec officielle (lecture directe du PDF) : **COLLECTION** (tracks avec `Location` obligatoire, métadonnées titre/artiste/album/genre/BPM/durée/rating, **AverageBpm**, **Colour** en RGB avec couleurs nommées comme Rose/Red/Orange/Yellow/Green/Aqua/Blue/Purple), **TEMPO** (beatgrid, plusieurs par track : Inizio/Bpm/Metro/Battito), **POSITION_MARK** (cues : `Cue=0, Fade-In=1, Fade-Out=2, Load=3, Loop=4` ; hot cue A/B/C = "0"/"1"/"2", memory cue = "-1"), et **PLAYLISTS** (arborescence dossiers/playlists référençant les tracks). · PDF spec ci-dessus.
- **Absences confirmées dans la spec XML** : aucune mention de **MyTags** ni de **smart/intelligent playlists**. Le XML ne sait pas représenter les smartlists — elles sont aplaties en playlists normales lors d'un export/sync. · https://www.lexicondj.com/manual/sync-rekordbox-xml et confirmé par l'absence dans le PDF officiel.
- **L'export XML a été retiré de l'UI dès Rekordbox 6** (l'import reste). C'est ce qui a cassé l'interop Denon/Engine. · https://community.enginedj.com/t/no-more-xml-export-in-rekordbox-6-blocks-denon-prime-users-to-access-their-rekordbox-collection/21170 ; l'export XML manuel n'existe plus, seuls l'import et la génération externe du XML subsistent.
- **L'import XML n'est PAS une fusion automatique en place** : les tracks/playlists du XML apparaissent dans un volet séparé ([Bridge]/Imported Library) ; pour les faire entrer dans la collection il faut une **action manuelle** (drag des tracks vers la collection, ou clic droit → "Import to Collection / Import Playlist"). · https://www.mixo.dj/guides/tracks-to-rekordbox-via-xml ; manuel RB 7.2.3 https://cdn.rekordbox.com/files/20250925103803/rekordbox7.2.3_manual_EN.pdf.
- **Bug historique d'import (RB 5/6/7)** : importer une *playlist* ne met pas à jour les tracks déjà présents en collection ; il faut clic-droit sur les *tracks* pour pousser les métadonnées. L'import est donc surtout **additif** (ajoute ce qui manque), pas un vrai upsert fiable. · https://www.mixo.dj/guides/rekordbox-xml-import-bug ; https://forums.pioneerdj.com/hc/en-us/community/posts/115018141563.

**Librairie pyrekordbox (XML)**
- `pyrekordbox.rbxml` **lit ET écrit** le XML : méthodes confirmées dans le source `add_track`, `add_playlist`, `add_playlist_folder`, `add_tempo`, `add_position_mark`, **`tostring()`** et **`save()`**. · source master https://raw.githubusercontent.com/dylanljones/pyrekordbox/master/pyrekordbox/rbxml.py (lignes 1248–1420).
- Le module XML couvre bien les **cues** (`PositionMark`: types cue/fadein/fadeout/load/loop, hot+memory) et la **beatgrid** (`Tempo`). **Aucune** référence à MyTag/smart/intelligent dans le source XML (grep vide) → cohérent avec la spec. · même source.
- Repo : **licence MIT**, ~**415 étoiles**, dernière release **v0.4.4 (2025-08-17)**, testé sur RB **5.8.6 / 6.7.7 / 7.0.9**. Avertissement explicite : projet "still under development", **faire un backup** avant toute écriture. · https://github.com/dylanljones/pyrekordbox.
- Côté master.db (pour mémoire) : pyrekordbox annonce read + write **limité** ("only a few tables support adding or deleting entries"). · https://github.com/dylanljones/pyrekordbox.

**M3U8 (ce que l'app fait en "live import" aujourd'hui)**
- M3U8 = simple **playlist UTF-8 de chemins de fichiers** (extension UTF-8 d'M3U). Il ne transporte **que** un ordre de pistes pointant des fichiers locaux : **pas de cues, pas de beatgrid, pas de couleurs, pas de MyTags, pas d'arborescence de dossiers de playlists, pas de hiérarchie smart**. Rekordbox sait importer un M3U8 comme playlist. (Format standard ; aucune capacité métadonnée DJ.) Confiance haute sur les limites intrinsèques du format ; le comportement exact d'import dans RB est à confirmer dans votre code/manuel.

**PDB / device export (USB) et ANLZ**
- Le **device export** (`export.pdb`, fichiers `ANLZxxxx.DAT/.EXT/.2EX`) est le format **lecture seule côté lecteurs CDJ/XDJ**, généré par Rekordbox pour les clés USB/SD. ANLZ = waveforms, beatgrids, index temporels, memory cues/loops. `.DAT` = ancien matériel, `.EXT`/`.2EX` = données étendues (waveform couleur HD). · https://github.com/Holzhaus/rekordcrate ; https://djl-analysis.deepsymmetry.org (Deep Symmetry / crate-digger).
- **Non pertinent pour gérer la collection principale** : c'est un artefact de sortie destiné aux platines, pas la source de vérité ni un canal d'import vers la collection. Les libs (rekordcrate Rust, crate-digger Java, pyrekordbox ANLZ) sont surtout orientées **parsing/lecture**.

### Verdict (orienté robustesse + légèreté + performance, macOS+Windows, UI web)

- **L'écriture directe du master.db est un "mal nécessaire" SI le produit doit préserver l'expérience sans friction et la fidélité totale** (cues/MyTags/smartlists conservés, mise à jour en place, pas d'étape manuelle). Aucun format d'échange ne réintègre MyTags ni smartlists : le XML les perd à l'aller comme au retour. Pour un outil de *sync de playlists téléchargées*, le coût fonctionnel du XML est surtout l'**action manuelle d'import** + le **caractère additif/non-upsert**, pas la perte de cues (le XML les porte) — c'est plus tolérable que pour un gestionnaire de bibliothèque complet.
- **La voie XML est nettement plus sûre et plus légère** : elle **élimine** le risque #1 (corruption SQLCipher, clé 6.6.5+, verrou "Rekordbox doit être fermé"). On écrit un fichier `.xml` à part avec `pyrekordbox.rbxml` (MIT, lecture+écriture confirmées, `save()`/`tostring()`), Rekordbox importe quand l'utilisateur le décide, et la collection de l'utilisateur n'est **jamais touchée en place** par votre app. Zéro chance de corrompre `master.db`.
- **Compromis fonctionnels à assumer côté XML** : (1) **import manuel** requis dans Rekordbox (volet Bridge), pas de "sync en temps réel" ; (2) comportement **additif/buggé** sur les tracks déjà présents (bug historique 5/6/7) → bon pour "ajouter de nouveaux morceaux/playlists", mauvais pour "modifier finement l'existant" ; (3) **perte MyTags + smartlists** (mais probablement hors scope d'un downloader Deezer) ; (4) **chemins de fichiers absolus** dans `Location` doivent être exacts par OS (macOS vs Windows), sinon tracks "introuvables".
- **Stratégie recommandée pour vos 3 priorités** : faire de **l'export XML le mode par défaut/robuste** (léger, zéro corruption, multiplateforme, n'impose pas de fermer Rekordbox), et réserver l'écriture master.db à un **mode "avancé/expérimental" opt-in** avec backup automatique obligatoire et garde "Rekordbox fermé". Cela découple la sûreté du produit de la fragilité SQLCipher.
- **M3U8 reste utile mais minimaliste** : suffisant pour pousser un *ordre de pistes*, mais perd cues/beatgrid/couleurs et toute hiérarchie. À garder comme fallback ultra-simple, pas comme format principal si vous voulez transmettre cues/beatgrid (là le XML est strictement supérieur).
- **PDB/ANLZ : à écarter** pour la gestion de collection — c'est de la sortie platine en lecture, non un canal d'import.

### Incertitudes / à confirmer
- **Comportement exact d'import M3U8 dans Rekordbox 7** (crée-t-il une playlist plate, gère-t-il les sous-dossiers, dédoublonne-t-il ?) : non vérifié en détail, à tester sur votre version cible.
- **Fiabilité de l'upsert XML en v7.x** : le "bug" qui empêche la mise à jour des tracks existants via import-playlist est documenté pour 5/6/7 mais son comportement précis (et tout contournement officiel récent) mérite un test manuel sur votre RB.
- **`add_position_mark` / fidélité des cues à l'aller-retour** : pyrekordbox écrit bien `POSITION_MARK`, mais la *couleur* des memory cues n'est pas dans le XML (limite signalée par Lexicon) — à valider si vous tenez aux couleurs de cues.
- **Résolution des chemins multiplateformes** (`Location` file:// encodage URI, volumes macOS vs lettres Windows) : à tester pour éviter le "file could not be found" (cohérent avec votre note mémoire sur la résolution de chemins).
- **Spec XML PDF** : datée 2020 (RB 6 récent), aucune mise à jour publiée pour 7 ; le format reste 1.0.0, mais une vérif sur un export généré par RB 7 confirmerait qu'aucun champ n'a divergé.
