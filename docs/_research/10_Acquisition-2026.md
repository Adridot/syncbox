### Constat (faits sourcés)

> **Réserve de sourçage transversale** : dans la recherche d'origine, les champs `sources` des deux options ET de la reco étaient **VIDES** — aucune source primaire citée à l'appui. Les faits ci-dessous ont été corroborés/réfutés par les deux sceptiques via vérification indépendante à la source (API GitHub, pyproject, code v2.2.0, libraries.io, Socket.dev). Les liens vérifiables apparaissent ci-dessous ; là où la recherche n'a fourni aucune URL, le fait est marqué « vérifié à la source par le sceptique » sans inventer d'URL.

**streamrip (lib Python, pas la CLI) — candidat recommandé**
- Downloader scriptable GPL-3.0 (`nathom/streamrip`), 4 728 ★. Dépôt **réellement maintenu** : tag **v2.2.0 daté 2026-03-12** (SHA `189acda489927719aa8591f6acdd7d67aecf929b`), changelog « Fix Deezer URL parsing (#820, #824) », **dernier commit 2026-04-21** (PR #942) · vérifié à la source (API GitHub) par le sceptique SOURCES.
- **PIÈGE MAJEUR : PyPI est figé à v2.1.0 (2025-03-10)**, qui contient ENCORE le bug de parsing d'URL Deezer post-juin 2025 → `pip install streamrip` ne donne PAS le correctif. Il faut **épingler sur le tag git** (`git+https://github.com/nathom/streamrip@v2.2.0`) ou vendoriser · vérifié à la source.
- S'importe comme bibliothèque : objet `Track` avec `async def download()` ; l'attribut `download_path` est posé par `_set_download_path()` puis mis à jour dans `postprocess()` à la conversion (= `engine.final_fn`) → **chemin de sortie réel sur disque, réalise D18** · vérifié dans le code v2.2.0.
- Stack : **mutagen ^1.45.1, pycryptodomex ^3.10.1, aiohttp ^3.9, deezer-py épinglé exact à 1.3.6** (PAS 1.3.7), + deps CLI (click-help-colors, simple-term-menu/pick, windows-curses) · vérifié dans `pyproject.toml`.
- Décryptage du flux : `from Cryptodome.Cipher import AES, Blowfish` — **import STATIQUE** en tête de `downloadable.py` (capté par l'analyse statique PyInstaller) · vérifié dans le code v2.2.0.
- `pycryptodomex` est en **namespace `Cryptodome`** (≠ `Crypto`) → **pas de collision PyInstaller** avec le `Crypto.Cipher.AES` du chiffrement PYZ · corroboré.

**deemix (lib Python) — fork vietsman/buoyantbeaver**
- La lib Python `deemix` (RemixDev, GPL-3.0) est la plus **mince** et la plus orientée embarquement (« barebone deezer downloader library »). `Downloader.download()` **renvoie un dict `{'path': str(writepath), 'filename': ...}`** et l'empile dans `downloadObject.files` → D18 le plus net · `returnData['path']=str(writepath)` puis `downloadObject.files.append(returnData)` confirmé en source.
- Stack minimale : click, pycryptodomex, mutagen, requests, deezer-py>=1.3.0 (**pas d'aiohttp**) → bundle plus léger.
- **Upstream Python mort** : l'original RemixDev/deemix-py est figé à v3.6.6 / deezer-py 1.3.7 (dernier commit 2022-01-11) ; PyPI `deemix` 3.6.6 = 2022-01-11. Le seul Python « vivant » est le fork **vietsman/deemix-py (alias buoyantbeaver)**, mais quasi inerte : dernier commit 2025-08-22 « Add missing requirement », ~2 commits en 2024 — **pas de preuve de correctif de l'API Deezer juin 2025**.
- **ATTENTION confusion** : « deemix est mort » + les forks récents (bambanah/deemix Jan 2026, DeeplyDrumming/DeemixFix) sont du **JavaScript/TypeScript/Node — INUTILISABLES** comme lib Python embarquée.

**Socle commun (pourquoi la lib n'a pas à exister deux fois)**
- streamrip et deemix partagent **exactement le même socle** : `pycryptodomex` (Blowfish) + `mutagen` + `deezer-py 1.3.7` figé (2022-03-05) côté écosystème → **packaging PyInstaller identique**, pas de surface crypto supplémentaire. La compat Deezer réelle vient des **patchs maison de streamrip**, pas d'un client API maintenu.

**Risque supply-chain (full-track + sécurité)**
- L'API officielle Deezer **limite l'accès à des previews de 30 s** ; le full-download est précisément ce que le package malveillant **`automslc` contournait illégalement** · [Socket.dev, 2025-02-25](https://socket.dev) (article cité tel quel par la recherche, daté 2025-02-25). → impose **pin strict + audit du code embarqué**.
- Des sources 2025-2026 affirment que les changements **CDN Deezer 2024 bloqueraient le full-track**, en **contradiction frontale** avec « streamrip ship des fixes Deezer actifs jusqu'en 2026 ». Contradiction **NON tranchée par la doc**.

### Verdict (reco ponytail)

**Choix : `streamrip` importé comme bibliothèque (objet `Track`), épinglé sur le TAG GIT v2.2.0** (`git+https://github.com/nathom/streamrip@v2.2.0`, **commit `189acda…` résolu et figé dans le lockfile** uv/poetry), enveloppé derrière une interface mince maison `DeezerAcquirer.download(track_id) -> Path`. **Télécharger par ID numérique de piste** (résolu depuis l'ISRC), **jamais par URL courte** (contourne le bug de parsing juin 2025).

- **PyInstaller** : aucun hook crypto custom requis ; `pycryptodomex` est en namespace `Cryptodome` (pas de collision avec le `Crypto.Cipher.AES` du PYZ) ; mutagen et pycryptodomex sont collectés automatiquement par PyInstaller récent. (La reco d'origine suggérait `--hidden-import=Cryptodome.Cipher.Blowfish` « par prudence » — voir révision : c'est un **non-problème**, l'import est statique.)
- **Supply-chain** : vendoriser/auditer le code embarqué (rappel `automslc`, Socket.dev 2025-02-25) ; fixer une politique de mise à jour du commit pin (veille sur les correctifs Deezer du dépôt streamrip).

**Rationale (Ponytail)** : à socle strictement égal (pycryptodomex Blowfish + mutagen + deezer-py), on choisit le **dépôt réellement maintenu** (streamrip, commits jusqu'au 2026-04-21) plutôt qu'un **fork Python fantôme** (vietsman/deemix-py, ~3 commits 2024-2025). Maximise robustesse (priorité n°1) et maintenabilité (garde-fou co-égal) sans coût de packaging supplémentaire. La paresse = réutiliser un downloader mûr derrière une interface mince, au lieu de réécrire la chaîne gw-light → track token → license_token → CDN → déchiffrement Blowfish soi-même.

**Ce que ça écarte** : (1) réécrire un downloader Deezer maison ; (2) le PyPI de streamrip (2.1.0, parser cassé) et celui de deemix (3.6.6, upstream mort) ; (3) tous les forks deemix JS/Node (bambanah, DeemixFix) inutilisables en Python ; (4) un hook PyInstaller crypto élaboré.

**Quand basculer (`addWhen`)** : passer à la lib Python **deemix (fork vietsman, commit vendorisé)** SI l'API interne de streamrip (Track/RipCore, non documentée) casse de façon répétée à l'upgrade et rend le wrapper ingérable, OU si le poids d'aiohttp + deps CLI devient un problème de bundle. Et **lancer un POC empirique AVANT de figer le choix** : valider qu'un **ARL Premium courant télécharge un FLAC/MP3 complet (pas un preview 30 s)** sur **macOS ET Windows**.

> Cohérent avec la décision tranchée « **lib laissée au build après POC** » : le choix streamrip@v2.2.0 est le défaut documenté, mais n'est verrouillé qu'une fois la porte POC franchie (ci-dessous).

### Incertitudes / POC à faire

> **PORTE BLOQUANTE (exigée par le sceptique 2)** : aucune verrouillage de Fork D ni de la lib avant que ces deux points soient levés empiriquement.

1. **[PORTE BLOQUANTE] Viabilité du téléchargement COMPLET à prouver** : des sources (synthèse viwizard/deezer-python 2025) affirment que les changements CDN Deezer 2024 limiteraient au **preview 30 s**, alors que streamrip ship des correctifs Deezer actifs jusqu'en 2026. **Contradiction non tranchée** par la doc, Socket.dev (2025-02-25) confirmant la restriction 30 s côté API officielle → **POC obligatoire** : un **ARL Premium réel** télécharge bien un **FLAC/MP3 complet** (pas un preview) sur **macOS ET Windows** avant de verrouiller Fork D.
2. **[RISQUE DOMINANT — révisé] Stabilité de l'API lib de streamrip** : l'interface Python (`Track.download`/`download_path`, `RipCore`, `PendingSingle.resolve`) **n'est PAS documentée et est de l'API interne** ; `Track` est un `@dataclass(slots=True)` non-constructible standalone (exige Config+Client+Database) et `slots=True` interdit le monkeypatch d'amortissement. Figer le commit exact, **écrire le wrapper en reconstruisant le chemin `PendingSingle.resolve` → `Track`** (PAS un `Track` instancié à la main), et tester qu'il survit aux upgrades. **Le wrapper n'est PAS de ~30 lignes** ; risque de casse silencieuse non quantifié.
3. **Commit git exact à épingler** : v2.2.0 est un tag GitHub absent de PyPI ; résoudre le SHA (`189acda…`) et le geler dans le lockfile (uv/poetry) pour reproductibilité — non fait ici.
4. **Décryptage Blowfish sous PyInstaller en binaire gelé** : confirmer sur un build réel macOS ET Windows que `Cryptodome.Cipher.Blowfish` est bien embarqué et que le déchiffrement aboutit. **NB (révisé)** : l'import est **statique** (`from Cryptodome.Cipher import AES, Blowfish`), donc `--hidden-import` est *a priori* un **non-problème** — vérifier quand même que l'analyse statique ne le rate pas en pratique, sans le sur-spécifier d'avance.
5. **Résolution ISRC → track id Deezer** : Syncbox doit mapper l'ISRC Spotify vers un ID de piste Deezer (via gw-light/search) AVANT download ; chemin non détaillé par les sources, à spécifier — c'est ce qui contourne le bug d'URL courte juin 2025 (télécharger par ID numérique, jamais par URL courte).
6. **Supply-chain** : auditer le code embarqué (rappel `automslc`, Socket.dev 2025-02-25) et fixer une politique de mise à jour du commit pin (veille sur les correctifs Deezer du dépôt streamrip).
