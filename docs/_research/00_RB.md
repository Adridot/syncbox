## Librairies d'accès à la base Rekordbox 'master.db' (SQLite/SQLCipher), tous langages

### Constat (faits sourcés)

**La clé SQLCipher du master.db — le point central**
- La clé du `master.db` (Rekordbox 6 et 7) est une **valeur fixe, identique sur toutes les machines/installs**, codée en dur dans l'appli Rekordbox. C'est de l'obfuscation, pas une vraie sécurité par-machine · [discussion #97 pyrekordbox](https://github.com/dylanljones/pyrekordbox/discussions/97) (« The key is still the same as in earlier Rekordbox versions ») et [recherche confirmée par tooling](https://github.com/liamcottle/pioneer-rekordbox-database-encryption).
- La clé est publiquement connue : `402fd482c38817c35ffa8ffb8c7d93143b749e7d315df7a81732a1ff43608497` (passée à `PRAGMA key = '...'` après `sqlcipher master.db`) · [liamcottle/pioneer-rekordbox-database-encryption](https://github.com/liamcottle/pioneer-rekordbox-database-encryption/blob/master/README.md).
- **Ce qui a changé à Rekordbox 6.6.5** : Pioneer a obfusqué le contenu de `app.asar` (les fichiers JS passent de clair en .jsc / bytecode V8 compilé). Cela casse l'**extraction automatique** de la clé depuis l'app, **mais pas la clé elle-même**, qui reste la même · [discussion #97](https://github.com/dylanljones/pyrekordbox/discussions/97), [quickstart pyrekordbox](https://pyrekordbox.readthedocs.io/en/stable/quickstart.html).
- Conséquence pratique : sur 6.6.5+ / 7, pyrekordbox ne peut plus extraire la clé de l'app, mais propose `python -m pyrekordbox download-key` (télécharge la clé connue depuis des sources et l'écrit dans un cache), ou la saisie manuelle `Rekordbox6Database(key="...")` · [quickstart](https://pyrekordbox.readthedocs.io/en/stable/quickstart.html). Tant que Pioneer ne **change pas la clé** (ce qui n'est pas arrivé jusqu'à 7.0.9 testé), le déchiffrement reste trivial avec la clé connue.
- Risque résiduel signalé par l'auteur : si Pioneer change un jour la valeur de la clé, il faudra de nouveau l'extraire (d'où l'intérêt des outils de dump mémoire) · [discussion #97](https://github.com/dylanljones/pyrekordbox/discussions/97).
- Outils d'extraction par mémoire (utiles seulement si la clé change un jour) : `rekordlocksmith` (Python, **macOS only**, via LLDB, nécessite SIP désactivé) · [Bide-UK/rekordlocksmith](https://github.com/Bide-UK/rekordlocksmith) ; méthode debugger sur breakpoint `sqlite3_key_v2` documentée · [gist 0xdevalias](https://gist.github.com/0xdevalias/b803476793b56f7c45e6361799168eb0).

**pyrekordbox (Python) — la référence**
- Lit le `master.db` complet (tracks, playlists, artists, albums, genres, labels) ; **écrit** (add/delete) sur un sous-ensemble de tables : `DjmdContent`, `DjmdPlaylist`, `DjmdSongPlaylist`, `DjmdAlbum`, `DjmdArtist`, `DjmdGenre`, `DjmdLabel` · [README](https://github.com/dylanljones/pyrekordbox/blob/master/README.md), [quickstart](https://pyrekordbox.readthedocs.io/en/stable/quickstart.html).
- Smart/intelligent playlists et MyTags : **partiellement supportés et en évolution** — le support des conditions MyTag dans les smartlists a été ajouté via sous-requêtes, avec des bugs résiduels (ex. smart playlists vides) suivis dans les discussions · [discussion #110](https://github.com/dylanljones/pyrekordbox/discussions/110).
- Maturité : **la plus mûre du lot** — v0.4.4 (17 août 2025), ~415 étoiles, 968 commits, 9 issues ouvertes, licence **MIT**, Windows + macOS, Python 3.8+. Versions Rekordbox testées : 5.8.6, 6.7.7, **7.0.9** · [GitHub](https://github.com/dylanljones/pyrekordbox), [PyPI](https://pypi.org/project/pyrekordbox/).
- Dépendance SQLCipher : wheels pré-compilés `sqlcipher3-wheels` (binaire SQLCipher inclus), installation manuelle possible · [README](https://github.com/dylanljones/pyrekordbox/blob/master/README.md). C'est la mémoire interne du projet : pyrekordbox importe `numpy` de façon eager (impact bundling).

**Alternatives qui visent VRAIMENT le master.db chiffré (hors Python)**
- **rbox (Rust)** : lit ET écrit le `master.db` v6/v7 chiffré via un ORM type-safe, lit/écrit aussi les ANLZ (waveforms, beat grids, hot cues). Feature `master-db` nécessite SQLCipher ; linking `bundled-vendored-openssl` par défaut (« no system dependencies », portable ; Windows requiert Strawberry Perl pour build OpenSSL). **Mais explicitement « experimental »**, v0.1.x, licence **GPL-3.0**, build de la dernière version en échec sur docs.rs · [docs.rs/rbox](https://docs.rs/crate/rbox/latest), [crates.io/rbox](https://crates.io/crates/rbox).
- **RDBManager (Node.js/Electron + Vite)** : lit ET écrit le `master.db` 6.x chiffré via **SQLCipher 4** ; écritures ciblées (hotcues/memory cues, BPM, beat grid). RB 6.x testé OK ; **7.x « may work, not yet verified »**. **Windows 10/11 x64 uniquement (pas de macOS)**, licence **GPL-3.0**, très petit projet (v2.1.1, ~21 commits, 3 étoiles). Avertit explicitement du risque de corruption · [l3x04/RDBManager](https://github.com/l3x04/RDBManager).

**Outils qui NE visent PAS le master.db (export-only) — pour ne pas se tromper**
- **rekordcrate (Rust, Holzhaus)** : parse **uniquement** les exports device (`export.pdb` DeviceSQL), ANLZ et settings ; **lecture/dump seulement**, aucun lien SQLCipher, ne touche pas le master.db. Licence MPL-2.0, projet actif (~670 commits) · [GitHub rekordcrate](https://github.com/Holzhaus/rekordcrate), [crates.io](https://crates.io/crates/rekordcrate).
- **crate-digger (Java, Deep-Symmetry)** : parse les media exports / ANLZ device (`export.pdb`), pas le master.db chiffré, lecture seule · [GitHub crate-digger](https://github.com/Deep-Symmetry/crate-digger). Le format PDB a été rétro-ingénieré par Deep Symmetry et al.
- Aucun équivalent trouvé visant le master.db **chiffré** en **Go**, **C#/.NET**, **Java/Kotlin**, **Swift** ou **C/C++** (non trouvé / à confirmer). Côté JVM, l'écosystème Deep-Symmetry ne couvre que les exports device.

**Faisabilité d'une réimplémentation : bindings SQLCipher par langage**
- Le verrou n'est PAS la crypto (clé connue + `PRAGMA key`), c'est (a) disposer d'un binding SQLCipher et (b) **réimplémenter toute la logique métier d'écriture cohérente** du schéma Rekordbox (FK, `UuidIDMap`, colonnes `rb_local_*`, `created_at`, etc.) que pyrekordbox encapsule déjà.
- Rust : `rusqlite` avec feature `sqlcipher` (ou `libsqlite3-sys` bundlé) — viable ; c'est ce que fait rbox.
- Node : `better-sqlite3-multiple-ciphers` ou `@journeyapps/sqlcipher` ; RDBManager prouve la viabilité via « SQLCipher 4 » en Electron.
- .NET : `Microsoft.Data.Sqlite` + `SQLitePCLRaw.bundle_e_sqlcipher` — binding existe (faisabilité technique du déchiffrement OK ; aucune lib métier Rekordbox existante).
- Go : `mutecomm/go-sqlcipher` ou builds CGO SQLCipher — binding existe ; aucune lib métier Rekordbox existante.

### Verdict (orienté robustesse + légèreté + performance, macOS+Windows, UI web)

- **Garder Python pour la couche Rekordbox n'est PAS strictement obligatoire** : il existe deux libs réelles qui lisent ET écrivent le master.db chiffré hors Python (**rbox** en Rust, **RDBManager** en Node). Mais ce sont des alternatives **immatures et limitées** — rbox est « experimental » avec un build cassé, RDBManager est Windows-only et n'écrit que cues/BPM/grid. Aucune n'approche la **couverture d'écriture ni la maturité de pyrekordbox**.
- **Pour la priorité #1 (zéro corruption)**, pyrekordbox reste de loin le choix le plus sûr : c'est le seul qui encapsule une logique d'écriture validée sur tables multiples (playlists, contenu, MyTags) et testée jusqu'à RB 7.0.9. Réimplémenter cette logique métier ailleurs (Rust/Node/.NET) est le **vrai risque de corruption**, pas la crypto.
- **La crypto n'est pas un verrou** : la clé est une constante publique connue ; n'importe quel langage avec un binding SQLCipher (rusqlite, better-sqlite3-multiple-ciphers, SQLitePCLRaw, go-sqlcipher) peut ouvrir le `master.db` en quelques lignes. Donc l'argument « seul Python sait déchiffrer » est faux.
- **Pour la légèreté (priorité #2)**, le talon d'Achille de pyrekordbox est le bundle : il importe `numpy` de façon eager (impossible à exclure du PyInstaller — cf. mémoire projet) + sqlcipher3-wheels → empreinte lourde et démarrage lent. Si la légèreté prime, **Rust (rbox/rusqlite+sqlcipher) donne le binaire le plus petit et le démarrage le plus rapide**, au prix d'une réimplémentation/durcissement de la couche métier write et d'une licence GPL-3.0 (rbox) à vérifier vs ta distribution.
- **Pour une UI web cross-OS sans process Python**, **Node + better-sqlite3-multiple-ciphers** est la voie la plus naturelle (RDBManager prouve la faisabilité de l'écriture chiffrée en Node/Electron), mais il faudrait porter manuellement la logique d'écriture playlists/MyTags de pyrekordbox — effort non négligeable et risqué.
- **Recommandation tranchée** : pour la robustesse, **garder pyrekordbox** comme couche Rekordbox (sidecar Python) et concentrer l'optimisation de légèreté sur le bundling Python (ou un sidecar Rust ciblé). Ne migrer la couche d'écriture vers Rust/Node **que** si la légèreté l'emporte clairement sur le risque — et alors prévoir un harnais de tests de non-régression sur le schéma master.db avant tout déploiement.

### Incertitudes / à confirmer
- **rbox** : capacités d'écriture exactes (quelles tables, transactions, cohérence FK), état réel du build (échec docs.rs sur 0.1.7) et activité récente du repo — à vérifier directement sur le repo GitHub de rbox (non consulté ici, seulement crates.io/docs.rs).
- Support **smart playlists / MyTags en écriture** dans pyrekordbox : fonctionnel mais avec bugs résiduels (discussion #110) — tester sur ta version cible avant de t'y fier.
- **Rekordbox 7** : la clé reste la même jusqu'à 7.0.9 testé par pyrekordbox ; confirmer pour les versions 7.x les plus récentes que Pioneer n'a pas changé la clé ni le schéma.
- **Licences GPL-3.0** de rbox et RDBManager : incompatibles avec une distribution propriétaire/fermée — à valider juridiquement si tu envisages de les intégrer (vs MIT de pyrekordbox).
- Faisabilité d'un **port Node/Rust de la logique d'écriture** : aucune lib existante ne couvre playlists/MyTags hors pyrekordbox — coût et risque à estimer par prototype.
- Aucune lib master.db trouvée en **Go / .NET / Swift / Java-Kotlin / C++** : « non trouvé », pas « confirmé inexistant » — une recherche GitHub ciblée par langage peut être refaite si une de ces stacks devient privilégiée.
