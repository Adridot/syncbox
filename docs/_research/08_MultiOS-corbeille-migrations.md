# Section 1 — Abstraction multi-OS (macOS + Windows)

## Constat (faits sourcés)

**Détection du process Rekordbox — psutil déjà bundlé via pyrekordbox**
- pyrekordbox (MIT, dépendance incontournable du projet) expose déjà `get_process_id(name)`, `get_rekordbox_pid()` et `get_rekordbox_agent_pid()`, bâtis sur `psutil.process_iter()`. La fonction strip le suffixe `.exe` via `os.path.splitext` (`rekordbox.exe` → `rekordbox`) pour un matching cross-OS, et compare par **égalité stricte de nom** (pas substring → pas de faux positif type `rekordbox-helper`) · [pyrekordbox utils.py](https://github.com/dylanljones/pyrekordbox/blob/master/pyrekordbox/utils.py).
- psutil est **dépendance directe** de pyrekordbox (`psutil>=5.9.0` dans son pyproject.toml, licence MIT), donc **déjà dans le bundle PyInstaller** — zéro dépendance ajoutée · [pyrekordbox pyproject.toml](https://github.com/dylanljones/pyrekordbox/blob/master/pyproject.toml).
- psutil est cross-OS (Linux/Windows/macOS/FreeBSD), maintenu activement (v7.2.x en 2026), `process_iter` + `disk_partitions` présents ; `NoSuchProcess`/`AccessDenied` documentés · [psutil GitHub](https://github.com/giampaolo/psutil), [psutil 7.2.x docs](https://psutil.readthedocs.io/).
- **Limite load-bearing pour §3.1** : la fonction pyrekordbox matche le **nom seul** (`proc.name()`), pas le `cmdline` ni le chemin exe — moins strict que le filtre actuel de `safety.py` qui vérifie que le chemin contient `/rekordbox.app/` ou finit par `/rekordbox`. Recommandation : garder psutil mais **réimplémenter le filtre strict en Python** (≈10 lignes : `proc.name() == 'rekordbox'/'rekordboxAgent'` + vérif chemin via `proc.exe()`/`proc.cmdline()` avec garde `AccessDenied`). Remplace `pgrep` (binaire macOS-only, absent de Windows), ce qui **débloque Windows**.

**Corbeille OS cross-platform — send2trash (D12, réversibilité de la suppression audio)**
- send2trash (v2.1.0, 14/01/2026, BSD-3-Clause, mainteneur arsenetar) est la lib de référence pour envoyer un fichier à la corbeille nativement, cross-OS, API une ligne `send2trash(path)`. macOS : `FSMoveObjectToTrashSync`/pyobjc (`NSFileManager`) — gère nativement les **volumes externes** (corbeille `.Trashes` par volume), crucial car les DJ travaillent sur disques/USB externes. Windows : `IFileOperation` (Vista+) si pywin32, sinon fallback `SHFileOperation`, avec `FOF_ALLOWUNDO`. pywin32/pyobjc **optionnels** (accélérateurs), fallback natif sans eux · [Send2Trash · PyPI](https://pypi.org/project/Send2Trash/).
- Dates de release confirmées : 2.1.0 = 2026/01/14, 2.0.0 = 2025/12/30, 1.8.3 = 2024/04/06 ; support Python 3.8–3.14 · [send2trash CHANGES.rst](https://github.com/arsenetar/send2trash/blob/master/CHANGES.rst).
- **LIMITE LOAD-BEARING D12 — exFAT/USB Windows** : sous Windows, les clés USB et volumes FAT32/exFAT **n'ont PAS de Recycle Bin par défaut → suppression DÉFINITIVE** (non réversible). Or exFAT est le format courant des clés DJ compatibles CDJ → la réversibilité D12 n'est **pas garantie** sur ce support · [Windows: pas de Recycle Bin sur USB/FAT32/exFAT](https://blog.7datarecovery.com/recycle-bin-on-external-drive/).
- **send2trash Issue #2 (lecteurs réseau Windows → suppression définitive)** · [#2](https://github.com/arsenetar/send2trash/issues/2). **Issue #28 (backend Windows peut supprimer réellement si fichier > corbeille, etc.)** · [#28](https://github.com/arsenetar/send2trash/issues/28).
- macOS : corbeille `.Trashes` par volume externe (par volume / par user) · [iboysoft .Trashes](https://iboysoft.com/wiki/trashes-folder-on-external-hard-drive.html).
- **Alternative écartée — plugin Tauri `trash` (crate Rust côté coque)** : techniquement la crate Rust `trash` a une couverture cross-OS comparable, mais déporter le delete vers la coque **casse l'ordonnancement transactionnel** (« supprimer les fichiers seulement APRÈS commit DB », §3.4, orchestré côté Python), ajoute un point de défaillance IPC sur une op critique, et ne résout PAS la limite OS de fond (USB/exFAT sans corbeille) · [crate Rust trash](https://crates.io/crates/trash).

**Chemins système & résolution de volumes — stdlib, pas de lib dédiée**
- Défauts confirmés par pyrekordbox/config.py : app data = `%APPDATA%/Pioneer` (Windows) vs `~/Library/Pioneer` ou `~/Library/Application Support/Pioneer` (macOS, **deux emplacements selon version** — détecter, ne pas supposer) ; install = `C:/Program Files/Pioneer` vs `/Applications`. La DB **n'est pas hardcodée** : pyrekordbox la résout via `masterDbDirectory` (lu dans `rekordbox3.settings`) + `options.json` sous `rekordboxAgent/storage/` · [pyrekordbox config.py](https://github.com/dylanljones/pyrekordbox/blob/master/pyrekordbox/config.py), [Pioneer DJ Community — emplacement DB](https://community.pioneerdj.com/hc/en-us/community/posts/22978339072153-Rekordbox-move-DB-within-PC).
- **Asymétrie volume-relatif macOS ↔ Windows** : macOS monte les volumes externes sous `/Volumes/<nom>` (le basename de `storage_root` = nom du volume), ce qui colle exactement à la règle volume-relatif existante (`/<NomVolume>/...`). Sous Windows il n'y a **pas de `/Volumes`** : un disque externe est une **lettre** (`E:\`) avec séparateurs antislash. La convention `/<NomVolume>/...` **n'est PAS directement transposable** et doit être abstraite par OS · [macOS /Volumes mount points](https://eclecticlight.co/2023/05/16/volume-names-mount-points-and-normalisation/), [NTFS volume mount points](https://en.wikipedia.org/wiki/NTFS_volume_mount_point).
- Aucune lib dédiée nécessaire : stdlib (`os`, `pathlib`, `sys.platform`/`platform.system`, `os.environ` APPDATA/LOCALAPPDATA, `Path.home()`) suffit ; `psutil.disk_partitions()` (déjà bundlé) est disponible pour énumérer les points de montage.

## Verdict (reco ponytail)

**Choix : psutil (déjà bundlé via pyrekordbox) pour la détection process + send2trash v2.1.0 pour la corbeille (D12) + stdlib (`os`/`pathlib`/`sys`/`os.environ`) plus `psutil.disk_partitions` pour les chemins/volumes.** Aucune lib lourde nouvelle ; send2trash est le seul ajout (5 deps légères, BSD). Confiance : **medium**.

Rationale : c'est l'option la plus paresseuse qui tient les non-négociables.
- **Détection process** — on remonte l'échelle ponytail jusqu'à « dépendance déjà installée » : psutil est tiré par pyrekordbox (confirmé `psutil>=5.9.0`), zéro ajout, et pyrekordbox expose même `get_rekordbox_pid`/`get_rekordbox_agent_pid` cross-OS. On garde psutil mais on **réimplémente le filtre strict** (`name == 'rekordbox'/'rekordboxAgent'` + vérif chemin via `proc.exe()`/`cmdline()` avec garde `AccessDenied`) pour préserver l'anti-faux-positif et le message amical du non-négociable §3.1. `pgrep` (macOS-only) disparaît → Windows débloqué.
- **Corbeille** — send2trash est la lib mûre, maintenue (v2.1.0, 14/01/2026), cross-OS native, une ligne, et gère les volumes externes macOS. Strictement mieux que réimplémenter `IFileOperation`/`FSMoveObjectToTrash` à la main, et préférable au plugin Tauri qui casserait l'ordonnancement « delete après commit » du sidecar Python.
- **Chemins** — stdlib suffit ; on lit master.db via pyrekordbox (`masterDbDirectory`) au lieu de hardcoder.

Ce qu'on écarte : (a) appeler directement la fonction pyrekordbox de détection (trop laxiste : match nom seul) au profit d'un filtre strict maison ; (b) le plugin/commande Tauri `trash` (casse la transactionnalité Python, même limite OS) ; (c) toute lib de disques dédiée (`psutil.disk_partitions` + `/Volumes`/lettres en stdlib suffisent) ; (d) tout hardcode du chemin master.db.

Quand durcir : (1) si un POC montre que send2trash échoue la garde TCC macOS depuis le sidecar (dossiers cloud) → envisager la commande Tauri `trash` pour cette op précise ; (2) si le format de chemin Rekordbox Windows diffère de la convention `/Volumes` → brancher `paths.py` par OS (lettre/antislash) ; (3) pour gérer le cas USB/exFAT/réseau Windows sans corbeille → pré-check du FS du volume cible + **avertissement UI** avant delete, voire fallback « copie vers un dossier `.trash` applicatif » pour préserver D12 ; (4) `AccessDenied` récurrent sur `proc.exe()` Windows → retomber sur le match par nom seul.

# Section 2 — Migrations de schéma SQLite versionnées (remplace B4)

## Constat (faits sourcés)

> Note de fidélité : dans le JSON, les tableaux `sources` de ce topic sont **vides** ; les URLs ci-dessous sont celles que les **deux sceptiques ont matérialisées et vérifiées** lors de la vérification adversariale (forum SQLite, cpython#112441, eskerda, Röthlisberger, PyPI yoyo/Alembic). Le sceptique SOURCES en a tiré un `needs-revision` (voir plus bas) : la prose de la reco surinterprétait ces sources.

**Pattern recommandé — PRAGMA user_version natif + scripts SQL ordonnés en stdlib**
- Un entier de version stocké DANS le fichier de base (`PRAGMA user_version`, slot d'en-tête géré par SQLite qui ne s'en sert jamais), un dossier `migrations/` de fichiers `0001_*.sql … 000N_*.sql` appliqués en ordre via `migrations[current_version:]`, chaque migration jouée dans une transaction puis `user_version` incrémenté. **Zéro dépendance** : tout est dans le module `sqlite3` de la stdlib, déjà présent (et déjà ouvert via sqlcipher3 pour master.db).
- Le **seed devient une migration ordinaire (0001)** jouée une seule fois car gardée par la borne de version → supprime mécaniquement le re-seed à chaque boot (**B4**).
- **Piège transactionnel connu** : `Connection.executescript()` fait un **commit implicite** de toute transaction en cours. Confirmé par **cpython#112441** : `autocommit=False` casse `executescript("BEGIN;...COMMIT")` avec `cannot start a transaction within a transaction` ; issue CLOSED as not-planned/invalid ; affecte Python 3.12+ · [cpython#112441](https://github.com/python/cpython/issues/112441). Il faut piloter `BEGIN`/`COMMIT`/`ROLLBACK` explicitement et **ne PAS combiner avec `autocommit=False`**, soit jouer les statements un par un dans une transaction gérée — sinon une migration multi-statements n'est pas atomique.
- `PRAGMA user_version = N` n'accepte pas de paramètre lié (statement, pas expression) : formater le `N` en chaîne (entier interne validé en amont, pas d'injection).
- Pas de rollback/downgrade fourni : on n'écrit que des migrations forward — le **backup horodaté SPEC-01 §9** sert de filet.

**Alternatives pesées (toutes plus lourdes, aucun bénéfice net)**
- **(b) yoyo-migrations** — lib + CLI en SQL brut, SQLite first-class, rollback + dépendances inter-migrations + table de tracking propre. Mais ajoute **3 deps transitives** (`sqlparse`, `tabulate`, `importlib-metadata>=3.6.0`), dernière release **v9.0.0 du 2024-08-10** (peu actif), `tabulate` = dépendance morte en sidecar HTTP, double emploi avec `user_version`. Licence Apache-2.0. Confirmé sur l'API PyPI · [pypi.org/pypi/yoyo-migrations/json](https://pypi.org/pypi/yoyo-migrations/json).
- **(c) Alembic** — référence SQLAlchemy, batch mode SQLite, downgrade, autogen. Mais tire **SQLAlchemy>=1.4.23 + Mako + typing-extensions** (+ tomli <3.11), suppose un **ORM** que le projet refuse (master.db ouvert via pyrekordbox/sqlcipher3), empaquetage PyInstaller non trivial (`env.py` + `versions/*` dans le `.spec`), alourdit le cold-start. v1.18.4. ## Verdict (reco ponytail)

**Choix : (a) PRAGMA user_version natif + scripts SQL ordonnés appliqués en stdlib `sqlite3`.** Confiance : **high**. C'est l'option la plus paresseuse de l'échelle ponytail : niveau 3 (feature native de la plateforme SQLite — le compteur de version vit dans le fichier .db et c'est SQLite qui le maintient) combiné au niveau 2 (stdlib `sqlite3`, déjà ouverte via sqlcipher3). Zéro dépendance ajoutée, zéro fichier de données externe obligatoire à empaqueter.

Pattern concret recommandé :
1. un dossier `migrations/` de fichiers `0001_init.sql`, `0002_*.sql` … numérotés en continu ;
2. au boot, lire `current = PRAGMA user_version` ;
3. pour chaque migration d'index > current, l'appliquer dans une **transaction EXPLICITE** : `con.execute('BEGIN')` ; jouer les statements ; `con.execute(f'PRAGMA user_version = {n}')` ; `con.commit()` (rollback sur exception), en pilotant soi-même `BEGIN`/`COMMIT` et **SANS combiner avec `autocommit=False`** (piège cpython#112441) ; éviter `executescript()` pour les migrations multi-statements qui doivent être atomiques, ou l'encadrer en connaissant son commit implicite ;
4. le **SEED initial devient la migration 0001** (ou un `INSERT` dans 0001/0002), donc joué exactement une fois et jamais re-joué — c'est précisément la suppression de **B4**. La table de version = le slot natif `user_version`, **pas une table applicative** (remplacer le `schema_migrations` actuel).

Ce qu'on écarte : le rollback/downgrade (forward-only, backup §9 = vrai filet) ; les deps inter-migrations et le locking multi-dev de yoyo (sans objet en mono-utilisateur) ; l'autogénération par diff d'Alembic (suppose un ORM, refusé) ; le diffing déclaratif (risque de transformation silencieuse des champs load-bearing 256/258 et chemins volume-relatif — inacceptable vs §9) ; tout binaire externe type dbmate.

Quand ajouter un framework (yoyo en priorité car Apache-2.0 + `.sql` brut, plutôt qu'Alembic) : (1) besoin réel de downgrade/rollback automatisé en prod ; (2) migrations assez nombreuses/complexes pour que la boucle stdlib génère des bugs récurrents ; (3) adoption d'un ORM SQLAlchemy ailleurs (alors Alembic devient cohérent) ; (4) plusieurs devs créant des migrations en parallèle (besoin de merge entre branches).
